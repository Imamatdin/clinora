## Decisions and changes

- **Browser-side parsing (deviation from "server parses").** Cloud Run limits (15 s app request timeout, 512 MiB, up to 2 instances) rule out a large single upload, and staging the dump server-side would store БЕМОРЛАР. The browser runs the same reader; the server re-validates every row (zod) and owns matching, prices and rejections. Security equivalence: an administrator can already write any catalog row by hand. Planner may overrule.
- **Assumed inner `.dt` layout** (documented in `src/modules/import1c/README.md`): top-level list per object, first string = full object name, records = lists of `{field, value}` pairs, UUID references. The container format is confirmed; the record layout is **not verified on a real file**. Field names go through an alias table.
- Migration `016_catalog_import.sql`: `is_active` on districts/mahallas/room_types; 1C-code unique indexes; `catalog_doctors`; `import_batches` / `import_batch_rows` (catalog rows only).
- `.dt` codes namespaced by 1C object (`МУОЛАЖА/…`) since several catalogs land in `services`. Room-type price -> bed service (`…/bed`). МУОЛАЖА kind inferred from names (consultation/diagnostic/surgery/procedure), shown in preview; an existing service keeps its kind.
- Import never deletes or clears; a field price differing from the price in force adds a row at commit time; dated register prices keep their date (midnight clinic time).
- Roles: import and catalog writes administrator only (brief); CEO may read. Расходлар not extracted (not in the brief's list); one-line addition if wanted for C5.
- Shared files touched with one line each: `routes/index.ts`, `web/modules.ts` (also removed the `module.departments` placeholder, now inside the catalog screen), `web/style.css`, `db/migrations/README.md`.
