## Delivered behavior
1. P1 offline: queued registrations are kept per owner (`user:device:clinic`). Switch user, sign-out and session expiry lock, never delete. Any user on that PC, including the PIN screen, sees "N offline registrations waiting for <name> to sign in"; the owner's next sign-in syncs them. Lost role or FORBIDDEN flags the bucket (kept) and shows CEO/administrators on that PC a blocked notice. Only device revocation deletes; the revoke confirmation names the count when this browser holds that device's queue.
2. P3 offline: a conflicting entry moves to the attention list; later entries keep syncing in order (entries with unfinished routing are also skipped, not blocking).
3. P1 pickers: `visitOptions` lists open inpatient visits with an active admission after their admission day closes (same rule as `visitForCharge`).
4. P2 discharge invoice: lines frozen at discharge; value/discount/paid/due computed live against those lines. `InvoiceView` gains `linesAsOf` and `paymentsAsOf`; UI and PDF print both.
5. P2 bed days: charge `created_at`/`completed_at` are the real posting time; price still resolved at the billed date; billed date stays in `bed_day_charges.charge_date` / `caretaker_day_charges.charge_date`.
6. P3 ward override: `services` accepts `override {reason, approverId, pin}`. Server requires a shared-PC session, an active CEO/administrator approver with a PIN, and the PIN; wrong PINs count in new `ward_override_attempts` (per approver+device, 5 tries, 15-minute lock), never on `account_pins`. Refusal returns 403 after commit. PIN is not stored in the replay payload. `dispense` takes the verified approver as a separate argument, never from a request body.
7. P3 dispense replay: patient access is rechecked first (revoked doctor still gets 403, existing test), then the idempotency key, then the open-visit check.
