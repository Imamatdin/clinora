# Task 005 — Clinical workflow, destination adapters and patient access

Issued 12 November 2026. Depends on task 004's immutable approved documents and task 003's linked channels. Read `../REMAINING-TASKS.md` and current integration/patient-link contracts before implementation. These are three required workstreams; completing one does not complete the task.

## Outcome

The clinician can turn explicit consultation decisions into reviewable follow-ups and referrals, reuse confirmed information, track delivery to a supported clinic system, and give a securely identified patient access to their released records. The UI distinguishes prepared, authorized, sent, acknowledged, failed and uncertain outcomes.

## A. Workflow actions

1. Implement typed action proposals with patient/clinic/encounter, action kind, exact instruction evidence or explicit manual author, due date with precision/timezone, destination, required fields, dependencies and revision. Start with follow-up tasks and referral preparation. Model-generated proposals cannot authorize themselves. Patient requests and quoted historical instructions are not current clinician decisions.
2. Show a review queue integrated with the encounter. Reuse approved/confirmed fields without asking for the same data repeatedly. Missing destination, recipient, date or required clinical detail stays unresolved. The clinician can edit, reject, approve, cancel and inspect action history. Any content/destination change invalidates the previous action authorization. Document approval and authorization to send a particular action are distinct records.
3. Use a transactional outbox and durable workers. Commit the authorized action, approved snapshot reference, audit and outbox entry atomically. At dispatch recheck the initiating actor's relevant authority, patient assignment, destination configuration and snapshot/action validity; expired browser cookies alone should not invalidate a deliberately authorized durable job, but revoked clinical authority must block it. Do not hold a database transaction open during network requests.
4. Define retry semantics by failure point. A timeout after a possible external write is uncertain; reconcile by a stable external/idempotency reference before resending. Never promise exactly-once external delivery without destination support. Store safe response metadata and external IDs, not secret-bearing responses. Concurrent workers, expired leases and process restarts must not authorize duplicate actions.
5. Follow-ups include an internal due-work list that works without external messaging. A notification is sent only to a verified destination through an explicitly configured channel and authorized workflow. Do not infer a phone number/email recipient or send clinical details in generic reminders. Cancellation after an external system may have acted requires reconciliation, not a false “cancelled everywhere” badge.

## B. Destination integration

6. Obtain the actual first clinic destination and its authorized interface. Implement one real adapter when that interface and test credentials are available. Record endpoint/version, supported operations, patient-ID mapping, authentication, payload/units, error classes, acknowledgement semantics and reconciliation capabilities. Prefer documented authorized APIs or supported imports; do not use clinician credentials to scrape an undocumented system or treat the supplied 1C connection profiles as an integration contract.
7. Keep adapters behind the existing port and extend it deliberately where needed. An adapter accepts the exact approved snapshot and action envelope, not a mutable current chart. External identifiers are clinic/destination scoped; ambiguous patient matches require resolution. No automatic merge by name/phone. A read-only destination cannot report a document write as succeeded.
8. Build a destination emulator/contract suite for deterministic CI and a useful manual export handoff. Mark them as simulated and manual respectively. If real access is unavailable, finish the adapter architecture, workflow and patient portal, but report the live destination as BLOCKED. A simulator or exported PDF is not completed live integration. Do not invent a DMED or 1C API.
9. Expose an integration status/history screen with the authorized source version, attempts, acknowledgement/external ID, last safe error and reconciliation actions. Only permitted operators can retry/reconcile, and a retry cannot silently select a newer document. Resolve updated/cancelled/amended documents through explicit action semantics; no silent overwrite of an external record.

## C. Patient account and released record access

10. Implement patient accounts using the same identity foundation and an explicit patient-link workflow. A clinic-authorized operator records an identity-proof reference and approves the chart link; proof must not be a name/phone match alone. Use expiring single-use invitations and server-side role separation. Keep proof details minimal and protected. Professional verification, clinical membership and patient access are separate grants.
11. A patient sees only records explicitly released to that verified link: visit timeline, permitted approved documents, clinic/date/clinician and released follow-up information. An approved clinician document is not automatically released to the patient. Keep drafts, internal comments, raw audio/transcripts and other patients' records out of patient APIs, searches, events and exports. Allow link/release revocation with audit and enforce it on the next request/download. Already downloaded copies cannot be remotely recalled.
12. One person may have multiple separately verified clinic links, but there is no automatic cross-clinic chart merge or clinician visibility. Default this increment to directly verified adult access. Guardian/delegated access remains a named unresolved requirement until the founders supply its authority and release rules; reject unsupported delegation rather than quietly granting it.
13. Include the owner workflows needed to operate these controls: assign/unassign clinicians to patients, block/revoke membership, issue/revoke patient invitations, approve/revoke patient links and release records. Owner administration does not itself grant chart-reading authority. Record all authority changes and preserve the separation already established in task 002.

## Acceptance

- Demonstrate an explicit clinician instruction -> draft referral/follow-up -> correction -> action authorization -> outbox -> destination acknowledgement/reconciliation -> history. Repeated transcript segments or retries cannot create duplicate authorized actions. Patient-only requests and ambiguous dates remain proposals/missing fields.
- Real PostgreSQL tests cover atomic outbox creation, worker crash before/after send, conflicting workers, revoked access before dispatch, amended source, destination timeout, duplicate callbacks, identity mismatch and audited reconciliation. A lost acknowledgement must not be labelled a definite failure or trigger a blind repeat write.
- Run the adapter contract suite, then a separately authorized synthetic test against the actual destination test environment. Record external IDs and safe evidence. If no test interface exists, explicitly identify the remaining live check; a production clinical write is not a substitute for a test environment.
- Two patients, two clinics and multiple clinician scopes: patient A cannot enumerate B, read an unreleased/withdrawn document, acquire doctor privileges, forge a link, reuse an invitation or retrieve clinical content through cached responses. Test role changes, stale sessions and subscription revocation.
- End-to-end patient journey on a phone: accept verified linking process -> view released timeline -> open/download exact released approved document -> see updated release status. Concurrent release/withdrawal and export must preserve the intended authorization boundary.
- Repeat existing capture, clinical approval and replay-isolation regressions. Review all messaging for recipient verification and minimal content; CI must not contact real recipients or live clinical destinations.

## Handoff

Report workflow, destination and patient access separately, with implemented/tested/live-blocked status. Provide action transition rules, adapter documentation, setup/rollback instructions, source/CI evidence and a list of unresolved external/guardian rules. Preserve the full scope if one external dependency is missing. Task 006 must expose that limitation in the presentation and release decision rather than hiding it.
